# Промпт для Google AI Studio: Android-клиент «НарядAI»

Вставить целиком в Google AI Studio (Build). Результат положить в `apps/android/native/`
и проверить по правилам раздела «Android-приложение» в `AGENTS.md`.

---

Сделай Android-приложение на Kotlin + Jetpack Compose (Material 3, minSdk 26) — тонкий клиент
системы нарядов на ремонт «НарядAI» для горно-обогатительной фабрики. Все данные демонстрационные.

## Главное правило: никакой бизнес-логики в приложении
Приложение только показывает данные и отправляет действия. Оно НЕ решает, какой переход статуса
разрешён, НЕ проверяет права, НЕ считает просрочку, рейтинг и статистику. Всё это делает сервер.
Если сервер вернул ошибку — показать её текст как есть.

## Бэкенд
- Supabase: URL и anon key берутся из `local.properties` (`SUPABASE_URL`, `SUPABASE_ANON_KEY`),
  в коде их нет. Библиотека: supabase-kt (auth-kt, postgrest-kt, realtime-kt, storage-kt).
- Вход: логин и пароль. Логин превращается в email `<логин>@naryad.local`,
  `signInWithEmail`. Сессию хранить, при 401 обновлять токен, при неудаче — на экран входа.
  Выход — только из этого устройства (scope = LOCAL).
- Роль и ФИО: таблица `employees` (`auth_user_id = auth.uid()`), поле `role`:
  `worker`, `master`, `lead`, `operator`.
- Чтение: таблицы `work_orders` (с `equipment(name)`, `section:section_id(name)`,
  `assignee:employees!work_orders_assignee_id_fkey(full_name)`), `work_order_events`, `photos`,
  `notifications`, представление `worker_board`. Правила доступа на сервере сами отфильтруют,
  что видно этому пользователю.
- Действия с нарядами — ТОЛЬКО через HTTP-маршруты веб-приложения
  `https://naryad-ai.vercel.app/api/mobile/...` с заголовком `Authorization: Bearer <access_token>`.
  Не вызывай напрямую RPC `transition_order`, `complete_order` и подобные: после них сервер
  запускает ИИ-проверку и уведомления. Маршруты:
  - `POST /api/mobile/orders/{id}/transition` `{ action, reason?, reasonCode?, clientActionId }`
    action: accept, queue, reject, start, pause, resume, help.
  - `POST /api/mobile/orders/{id}/complete`
    `{ workDone, faultCode?, materials: [{materialId, qty}], clientActionId }`.
  - Фото: загрузить в Storage bucket `photos` по пути `{orderId}/{kind}-{uuid}.jpg`
    (сжать до 1600 px, JPEG 80, удалить EXIF), затем
    `POST /api/mobile/orders/{id}/photos` `{ kind: "before"|"after", path }`.
  - Голос: `POST /api/voice` (multipart, поле `audio`, m4a/wav) → `{ text }`.
  `clientActionId` — UUID, создаётся один раз на нажатие. При повторе после обрыва сети
  отправляется тот же, сервер не задублирует действие.
- Realtime: подписка на изменения `work_orders` и `notifications` этого пользователя → обновить список.

## Экраны (версия 1 — исполнитель)
1. Вход: логин, пароль, «Показать пароль», переключатель Рус/Қаз.
2. Мои наряды: сверху аварийные (красные), затем по сроку. Карточка: «№номер», описание
   (2 строки), исполнитель, оборудование · участок, срок, плашки приоритета и статуса,
   «Просрочен на N мин», если сервер вернул такой признак или `due_at < now` (только показ).
3. Наряд: всё о наряде, история из `work_order_events`, фото. Внизу одна главная кнопка
   по текущему статусу (Принять / Начать / Завершить) и меньшие (Пауза, В очередь, Отклонить,
   Нужна помощь). Пауза и Отклонить открывают лист с обязательной причиной (кнопка неактивна,
   пока причина пустая).
4. Завершение: «что сделано» (текст или диктовка), шифр неисправности, материалы,
   фото «после» (обязательно для внеплановых — проверку делает сервер, но подсказку показать).
5. Уведомления: список из `notifications`, отметка прочитанного.
6. Профиль: ФИО, роль, язык, выход.

## Интерфейс
- Рабочий в перчатках: кнопки не ниже 56 dp, главное действие внизу экрана, крупный текст.
- Цвета: тёмно-синий фирменный `#0B2A5B`, акцент жёлтый `#F5C400`, аварийное — красный.
  Статусы исполнителя: зелёный — свободен, жёлтый — в работе, синий — очередь, серый — не на смене.
- Все надписи в `strings.xml` (ru) и `values-kk/strings.xml` (kk). Никакого текста в коде.
- Без сети: показать последние загруженные данные и плашку «Нет связи». Действия складывать
  в очередь (Room) с clientActionId и отправлять при появлении сети.
- Пустые и ошибочные состояния говорят, что делать дальше.

## Чего не делать
- Не запускать модели ИИ на телефоне.
- Не хранить в коде ключи, пароли и service_role.
- Не менять статус наряда записью в таблицу — только через маршруты выше.
- Не добавлять функции, которых нет в этом описании.
